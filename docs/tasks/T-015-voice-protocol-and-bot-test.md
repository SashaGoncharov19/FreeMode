## Goal

`PacketType.Voice` carries 20 ms Opus frames (48 kHz mono, 24 kbit/s) on an unreliable channel; the server relays
each frame to players within `VoiceRange` (default 40 m, per-player override by the API) in the same dimension, with
`API.setPlayerVoiceChannel(player, channel)` / `mutePlayer` controls; two bots exchange frames through the server and
the test asserts delivery and jitter.

## Acceptance criteria

- [x] Bot A sends 5 s of voice; bot B within range receives ≥ 245 of 250 frames with p99 inter-arrival ≤ 40 ms; bot C out of range receives 0 — phase 3 of `eng/integration-test.sh`: the talker sent 250 frames in 5.0 s; the listener 5 m away received 250 with inter-arrival p50 16.1 ms / p99 33.1 ms; the player 990 m away received 0.
- [x] Server CPU for relaying 100 talkers × 50 frames/s measured with the T-002 harness: `LOAD_VOICE=1 LOAD_MOVE=0 eng/load-test.sh 100 60` — 100 talkers standing at freeroam's four spawn points (about 25 within earshot of each other), 50 frames/s each: the server took 4 660 frames/s in and relayed 115 000 frames/s (plus the sync relay of 100 players), tick p50 1.1 ms / p99 2.5 ms at 58 ticks/s, 0.8 CPU-core in total (33.6 CPU-seconds over 40 s), 141 MB RSS, no voice frames dropped; egress 94 KB/s per player (1 509 packets/s, voice and sync together).

## Result

* **Decisions inside the task**: channel 0 = proximity voice (the talker's range, default `<voicerange>` 40 m, per-player
  override), channel N > 0 = radio (everyone on channel N, any distance, no dimension check); mutes are per listener per talker;
  the server never decodes; a frame is at most 400 bytes and a player may send 60 frames/s (a 20 ms cadence is 50/s); the relayed
